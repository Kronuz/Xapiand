## ═══════════════ PROJECT DIRECTIVES (read first — apply to ALL work) ═══════════════

**The generalized, project-agnostic methodology lives in its own file:
`~/Development/Kronuz/KRONUZ_REFACTORING_DIRECTIVES.md` ("Kronuz Refactoring Directives")** —
read it for the full doctrine (north star, prime directive, extraction principles, the couplings
table, the "complete" criterion, the deliverables standard, perf/reliability discipline, mechanics,
and the extraction checklist). The section below is the *Xapiand-specific application* of it.

**The vision (north star).** Disassemble Xapiand into **many small/medium, generic, reusable
libraries**, and make the app itself **as few lines as is feasible and technically possible**.
Xapiand becomes a thin composition of clean, extensible Kronuz/* components; every generic
seam gets extracted, and the app keeps only the irreducible domain glue (its types' app-specific
fields, its domain message handlers, its lifecycle policy).

**The core guardrail (non-negotiable).** Never lose **performance, final functionality, or
reliability.** Extraction is a *behavior-preserving* move, not a rewrite:
- **Faithful/verbatim port.** Move the proven logic as-is; route only the couplings (transport,
  node/membership, state hooks, apply) through injected seams. Keep the wire format byte-identical
  and the algorithm line-identical. Do NOT "improve" an algorithm during extraction (especially
  consensus — a subtly-wrong Raft is split-brain, not a bug).
- **Performance.** No regressions. Injected virtual seams are fine on control-plane paths (timers,
  gossip-rate messages) but must NOT sit in hot data paths; prefer compile-time (templates) there.
  Benchmark before/after when a hot path is touched.
- **Reliability.** Validate that behavior is identical (unit tests + the app's E2E/cluster nets).
- **Extensible enough, but honest.** Prefer a clean generic lib; if a piece is too app-fused to
  extract cleanly (its seams would be all app-specific hooks), **fall back to keeping it in the
  app** rather than shipping a fake-generic or unreliable lib. Say so explicitly.

**Every extracted lib MUST ship (the deliverables standard).** A lib is genuinely reusable — and
only then "done" — when it is **documented, demonstrated, measured, tested, and complete**:
1. **README.md** — what it is, the shape, a usage snippet, build/deps. (documented)
2. **ARCHITECTURE.md** — how the pieces fit + the data/control flow + the extension seams. (documented)
3. **AGENTS.md** — working notes + the invariants ("do not regress these") + build/test. (documented)
4. **examples/** (demos) — at least one runnable program showing real use, not just the test. (demonstrated)
5. **benchmarks/** — when it makes sense (a perf-relevant lib): a measured before/after or a
   throughput/latency harness. Skip only for libs where perf is irrelevant (say why). (measured)
6. **tests/** — unit/integration tests, green under ctest; cover the invariants + edge cases. (tested)
7. **COMPLETE** — the extracted bits let the app lose **nothing**: every function, every feature,
   and every performance optimization of the original is preserved **line by line**. The only
   acceptable deviation is an *improvement*. If the original had a dual buffered/streaming mode,
   a fast path, a specific socket-buffer sizing, a back-pressure knob — the lib carries all of it.
   A simplified subset is NOT an extraction; it is a regression. (complete)

Header-only + standalone-Asio where applicable; CMake INTERFACE target `<lib>::<lib>`;
FetchContent deps (`GIT_TAG main`, `-DFETCHCONTENT_SOURCE_DIR_<DEP>` for local dev); tests built
only when top-level. Publish public to `github.com/Kronuz/*` under identity `Germán Méndez Bravo
<german.mb@gmail.com>` on `main`.
